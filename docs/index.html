chapter 02 · the decision

Six gates, in order. A gate can only ever lower the verdict.

Question, evidence, verdict — six times, deterministically. Each gate can hold what the last one allowed, never the reverse, and BLOCK stops the ladder where it stands. Every gate stores what it resolved, so any decision replays bit-for-bit without touching the rail.

chapter 03 · the boundary

The model reads and writes English. Deterministic code touches the money.

Above the line the model interprets plain English into a mandate, at authoring time, behind a human approval. At runtime it is optional, and it can only ever hold or block. It cannot allow.

Below the line every rupee of arithmetic, every limit, every retry decision is code that can be read, tested and replayed — scope, value, limits, exactly-once, provenance, rail execution, ledger verification.

chapter 04 · the second failure

Then a good request was interrupted mid-flight.

act i  a wrong proposal never reached the rail
act ii  a correct proposal reached it — and the process died before the answer came back
  1. PROPOSED
    SIK derived from merchant, tool, subject, amount and reason. Row inserted.
  2. AUTHORIZED
    Gates 01–04 cleared. ₹2,800 refund on an approved return.
  3. IN_FLIGHT
    Write-ahead record fsynced before the call. Lease taken, +30s.
  4. process terminated

    The durable intent survived. The process did not.

  5. UNKNOWN
    Found on disk at boot, lease expired. A timeout is not a failure — we do not know what the rail did.

  6. Unknown never means retry.

  7. RECONCILING ×6
    Asking the rail what happened, with full pagination. Absence only counts once the pages run out.
  8. QUARANTINED
    Six passes, no answer. A named human decides — applied, or confirmed not applied. Never a blind retry.

Naive handlers map unknown to failed, failed to retry. That single mapping is the whole duplicate refund. Interlock writes the intent to disk before the call, so a dead process is recoverable — and never retried blind.

chapter 07 · the envelope

Interlock is deliberately small.

Naming the envelope precisely is the production signal. An unqualified claim is the demo signal.

it is

  • +Deterministic money controlsSix gates, in order, with the evidence each one resolved.
  • +Semantic idempotencyOne key per semantic action, durable before the rail is called.
  • +Mandate-bound executionTools the mandate does not grant are never listed to the agent.
  • +ReconciliationUnknown outcomes are resolved against the rail, or handed to a human.
  • +An auditable recordEvery proposal, verdict and the evidence each gate resolved, in a gapless hash-chained ledger.

it is not

  • −An LLM deciding paymentsThe model writes the policy. It never enforces it.
  • −A replacement for the payment railIt sits in front of the rail's own MCP server.
  • −A universal fraud engineIt enforces a mandate. It does not detect intent it was not told about.
  • −A multi-tenant enterprise platformSingle-tenant, single-process, SQLite.
  • −Magic AI safetyA control layer with a documented envelope, not a guarantee against every payment failure.

stated, not assumed

Single-tenant. Single-process. SQLite, no HA. The operator console is not in v0.1. Validated against a high-fidelity mock rail only — the live Razorpay adapter is not in v0.1, and --rail razorpay refuses rather than pretending. Purpose-checking is opt-in, advisory and not implemented. The benchmark’s headline delta comes from our own scripted harness, labelled as such in every table.
